# Phase 0 research: LiveUpdate object/property candidates for Designer r34.0.3

Generated from the Phase 0 research workflow (7 research agents, one adversarial verifier per dimension, one completeness critic; 19 agents, 603 tool calls). Sources: the official r34.0 Python stub `d3.pyi` (`__version__ = r34.0.256372`), developer.disguise.one (LiveUpdate API page, Monitoring Machine Health guide, Python API guides, Session API pages), help.disguise.one (expressions, graphs, failover, devices), and the disguise-one `grafana-liveupdate` and plugin example repositories.

**Status column** is the verifier's corrected confidence, which overrides the researcher's claim:

- `doc-verified`: a document shows the full LiveUpdate usage, or the member exists in `d3.pyi` **and** the object-path prefix is documented.
- `inferred`: the member exists in `d3.pyi` but reachability through that object path is not documented.
- `unverified`: plausible, no evidence.
- `reject`: the verifier found the claim wrong (misspelled member, wrong class or arity).

Writable = `yes` means a Python setter exists (or the doc shows a set); it does **not** prove that a LiveUpdate `set` succeeds. Nothing in this document has been tested against a live Director yet. `<PLACEHOLDER>` tokens follow the project convention (`<TRACK_NAME>`, `<SCREEN_NAME>`, `<MACHINE_NAME>`, `<WORKLOAD_ID>`, `<LAYER_NAME>`).

## Monitoring (local and remote metric monitors)

**Researcher summary.** Object-path prefix `subsystem:MonitoringManager` and the two lookup calls `findLocalMonitor(name)` / `findRemoteMonitor(nodeName, monitorName)` are doc-verified in both the LiveUpdate page and the Designer API guide "Monitoring Machine Health" (real URL: https://developer.disguise.one/api/guides/monitoring ; the guessed /monitoring-machine-health 404s). Every monitor is a `MetricMonitor` (d3.pyi:25989) whose only value accessors are `seriesAverage(title, nSamples) -> float` and `seriesAverageByIndex(idx, nSamples) -> float`; nSamples=1 is documented as "the latest value in the series", and the guide recommends a 10-sample rolling average for alerting. Documented (monitor name -> series title) pairs: "fps"->"Actual" (LiveUpdate doc + guide), "GPUProfiler"->"Total" (+ "Video Upload","Capture Upload","Compositor","GUI","Render Everything","DMX" from disguise-one's official Grafana dashboard), "CPU"->"Total", "GPUMemory"->"Usage(MB)", "ProcessMemory"->"Usage (MB)" (guide), "Machine"->"CPU Time","GPU Time","CPU Memory","GPU Memory","Disk" (Grafana dashboard, unit percent), "Disk"->"Read (MB/s)","Write (MB/s)" (Grafana dashboard; guide says Disk over LiveUpdate is still "in development (DSOF-20732)"). Remote node names are "<hostname>:d3" ("Replace MACHINE_NAME with the hostname of the target machine"). Discovery expressions (`object.remoteNodes()`, `[m.name for m in object.localMonitors().all()]`, `[s.name for s in object.graphDescriptor(False).dataSeries]`) exist in the stub but their LiveUpdate use is only inferred; `FifoDataSeries.samples()/capacity()` (raw buffer, min/max) are new in r34.0. Nothing in this dimension is sensibly writable from a Stream Deck (setters exist only for monitor config such as pollInterval/name). Recommended updateFrequencyMs: 500 for live readouts (fps, GPU/CPU ms), 1000 for rolling averages and the "Machine" percentages, 2000-5000 for memory, 10000+ for discovery lists; never 0 for monitors (per-frame pushes at 60 Hz). Embedded Python is 2.7 (use `False`, not `false`; dict/list comprehensions are fine).

**Verifier summary.** Verified all 28 candidates against freshly downloaded sources (guide, Live Update page dump, help.disguise.one graphs and RenderStream-graphs pages, r33.1/r34.0 change logs, Python environment page, disguise-one grafana-liveupdate dashboard JSON) and the local r34.0 d3.pyi. Every cited d3.pyi line number resolved to the exact member and signature quoted, and every document excerpt was found verbatim (guide at https://developer.disguise.one/api/guides/monitoring; the /monitoring-machine-health URL 404s as reported). 27 of 28 candidates are supported. The one rejection-level item is mon-renderstream-prefetcher-names: the 'renderstream'/'prefetcher' constants live on _BlipValue classes that are not MetricMonitors, and two of the series labels the researcher quoted ('network latency (ms)', 'engine latency (ms)') do not exist on the help page - marked unsupported/unverified. Confidence corrections: several direct members on documented object paths (remoteNodes, seriesAverageByIndex, monitor meta properties, RemoteMonitor.nodeName, Machine.nodeName, Subsystem.isEnabled, searchString) were upgraded from inferred to doc-verified under the brief's rule (pyi member exists AND object-path prefix documented); multi-hop chains through MonitorCollection (_BlipValue) or graphDescriptor() snapshots were held at inferred because no doc shows such intermediates traversed in a LiveUpdate expression. Writability corrections: RemoteMonitor.nodeName and MonitoringManager.searchString have pyi setters (writable yes, but do not ship set presets); GraphDescriptor fields all have setters but act on a per-call snapshot (keep unknown). Unit finding for the lead: the help page defines the CPU graph's 'Total Time (ms)' as working time + present-wait time in milliseconds, so the guide's 'CPU utilisation' heading is misleading - label the CPU Total readout in ms pending a live check. The 'Machine' monitor (percent series) and 'Disk' MB/s series come only from the official Grafana dashboard, not developer docs, and 'Machine' is absent from the help page's Local graph list - keep needs-live-test. Missed items of real operator value: Machine.hasIncomingHouseSyncSignal()/incomingHouseSyncSignal()/allRequiredOutputsGenlocked() give a genlock indicator over the doc-verified Machine:\"<name>\" path, filling the gap the researcher reported for the health endpoint's Genlock category. Sources saved locally (guide.txt, helpgraphs.txt, rsgraphs.txt, r340.txt, r331.txt, env.txt, grafana.json, pymm.txt, pymgr.txt, accessres.txt).

## Transport / track playback state

**Researcher summary.** CONCLUSION: transport state IS reachable from a LiveUpdate object expression, and the exact documented syntax is the one the module HELP already uses: object path `transportManager:default`, property paths under `object.player.*` (TrackPlayer), `object.track.*` (current Track), `object.timecode.*` (TimecodeTransport) and the TransportManager's own fields. Evidence: (1) Disguise's official plugin guide https://developer.disguise.one/plugins/getting-started/ subscribes exactly `autoSubscribe('transportManager:default', ['object.player.tRender'])` through the LiveUpdate Vue composable; (2) the Designer expression guide https://help.disguise.one/designer/configuration/expressions/accessing-resources uses `transportmanager:default.timecode` (lower-case type; both casings appear in official docs, the LiveUpdate-context one is camelCase); (3) the OSC monitoring guide documents `transport.player.playMode.__str__()`, `transport.brightness`, `transport.volume`, `transport.statusString`, `transport.tcStatusString`, `transport.beatToTimecode(currentBeat).__str__()`, `track.description`, `track.trigger_note`, `track.bpmAt(currentBeat)`, `track.noteAtBeat(track.sectionToBeat(currentSection))` where `transport` is 'The Transport Manager' and `track` is 'The current track within the transport' - in LiveUpdate `object` plays the role of `transport` and `object.track` the role of `track`; (4) d3.pyi r34.0 confirms every member and setter. The transports Python guide does NOT expose `d3.transportManager` or `TransportManager.default`; in Python the manager is reached via `guisystem.currentTransportManager` (GuiSystem is a Subsystem, so `subsystem:GuiSystem` + `object.player.tRender` is a plausible but untested alternative that would follow whichever transport is current). Key facts for preset design: `object.player.playMode.state` is the LIVE play state enum (Play=0, PlaySection=1, LoopSection=2, Stop=3, HoldSection=4, HoldEnd=5 per TrackPlayer constants) whereas `object.play_mode` is only the timecode-chase CONFIG with a different numbering (0 Play, 1 Play To End Of Section, 2 Loop Section) - do not confuse them. `object.brightness`, `object.volume`, `object.engaged` have setters (LiveUpdate-settable), but whether a LiveUpdate `set` on them behaves like a TransportCommand is undocumented. `object.player.speed` is new in r34.0. Playhead values (`tRender`/`tCurrent`) are in beats (== seconds at the default 60 bpm); use `object.track.beatToTime(...)` for guaranteed seconds and `object.beatToTimecode(...).__str__()` for a TC string. Designer eval is Python 2.7 (developer.disguise.one/python-api/environment: 'Designer uses Python 2.7 for its embedded interpreter'), so avoid f-strings; `__str__()`/`str()` and comprehensions are fine. REST /api/session/transport is command-oriented (all POSTs: play, stop, playsection, playloopsection, gotoframe/time/timecode/track/section/tag/note/next/prev, returntostart, brightness, volume, engaged) and its GET state endpoints (activetransport, transports, tracks, setlists, annotations) expose uid/name/engaged/volume/brightness/playmode(string)/currentTrack/receivingTimecode/setList - all of which except `receivingTimecode` map cleanly onto LiveUpdate properties listed below.

**Open questions:**

- tRender vs tCurrent: both are undocumented in the stub (PlayHead d3.pyi:33922/33926). Disguise's plugin guide uses object.player.tRender; the Python track guide uses guisystem.player.tCurrent for 'current playhead position (in beats)'. Which one the timeline readout follows (and whether tRender lags by a frame) needs a live check before choosing the preset default.
- Units: the LiveUpdate doc states all times are beats (track time); the plugin guide prints tRender with an 's' suffix. Beats == seconds only at the default 60 bpm. Presets should either document this or use object.track.beatToTime(object.player.tRender) (tr-03).
- Type-prefix casing: developer.disguise.one/plugins/getting-started uses `transportManager:default`, help.disguise.one accessing-resources uses `transportmanager:default`, the Python resources guide says paths are always lowercase, yet the LiveUpdate doc uses `Machine:"<name>"`. - 'default' is the documented name of the default transport manager (help accessing-resources). Projects with renamed or multiple transport managers need transportManager:"<name>" (tr-49) or getByUID(); no doc shows these with the transportManager type specifically. - Writing via LiveUpdate `set` on object.brightness / object.volume / object.engaged: setters exist in the stub and the LiveUpdate doc says set commands are undoable and persistent, but nothing documents whether such a set is equivalent to TransportCommand.makeBrightness/makeVolume (propagated to actors as a transport command). - JSON shape of object.player.playMode when subscribed directly (PlayMode is a _BlipValue structure with a `state` int) is untested; presets should subscribe to `.state` or `.__str__()`. The literal strings returned by PlayMode.__str__ are not documented anywhere I found.

## Stage / Screen objects

**Researcher summary.** Screens in Designer r34 are Resource > Object > Display subclasses: Screen2 (UI name "Surface" = projection surface), LedScreen, Projector, DmxScreen (via DmxDisplay > DownloadableDisplay), plus the Stage container (Object). LiveUpdate object paths use Designer expression syntax `type:name`, where `type` is the class name (the LiveUpdate doc uses `screen2:screen_1`; help docs use `projector:"projector 1"`, `videoclip:"sample/george.jpg"`, `module:video`, `transportmanager:default`; the LiveUpdate doc uses `Machine:"<machine name>"`). Names with spaces/special chars are either double-quoted (`projector:"projector 1"`, newer versions) or sanitised to underscores (`projector:projector_1`, all versions; only a-z A-Z 0-9 _ allowed). Any resource can also be reached by `getByUID(0x...)` (documented as a LiveUpdate object path). Only `screen2:` and `projector:` prefixes are documented; `ledscreen:` and `dmxscreen:` follow the same rule but are inferred, and no `stage:` prefix is documented at all. Geometry: Object.offset/rotation/scale are writable Vec values serialised as `{x,y,z}`; the LiveUpdate doc explicitly shows `screen2:screen_1` / `object.offset -> { x: 0.0, y: 3.0, z: 0.0 }` and that a partial set `{x: 4.0}` preserves the other fields. Operator-relevant writables common to every screen type (Display base): master_fade (0..1 output brightness, not shown in visualiser), holdOutput (freeze output), blendMode/alpha/content (visualiser compositing), renderLayer (On/Off stage/Frontplate/Backplate...), resolution. Type-specific: Screen2.projectorViewBlending/screenBackground; LedScreen.luminanceNits/viewingAngle (visualiser only); Projector.render_mode, simulatedShutterOpen, autoSoftEdge, feather, lumens, barnDoor*; DmxScreen.status__ (Mute/Active = DMX output kill), universe, iChannel, luminance. Valuable read-only state: description, isBad/isInError, isReceivingFromTrackingSource, hasTrackingSource, mesh.description, isConnected, Projector.hasFeedAssigned()/isActiveOutputModeNone, DmxScreen.isTableMalformed(), Stage.nDisplays(). Expression property paths are Python 2.7 eval'd with `from d3 import *`; list/dict comprehensions allow one-button multi-field readouts.

## Expression Variables and operator knobs

**Researcher summary.** Storage model (d3.pyi r34.0): ExpressionVariablesDevice(Device) has one writable property `container` (ExpressionVariablesContainer), whose `variables` is a writable `List[ExpressionVariable]`. Each ExpressionVariable is a _BlipValue (not a Resource) with writable `name` (str), `type` (int enum 0=Float, 1=String, 2=Function), `defaultFloat` (float), `defaultString` (str), `errorText` (str), plus `makeExpression() -> str`. There is no separate "value" field: the official "Set ExpressionVariable to a value" snippet on python-api/useful-strings writes `var.defaultFloat`, so for device variables defaultFloat/defaultString ARE the live value. Timeline (layer) variables live on ExpressionVariablesModule.fields -> List[ConnectedField] (each has `.variable` and `.value: ReflectionValue`, plus setFloat/setString). Object-path prefix: no page shows an ExpressionVariablesDevice referenced by expression; the documented convention is `<class>:<name>` (track:, screen2:, projector:, module:, transportmanager:default, Machine:"name", and for a Device subclass `mididevice:bcf2000`), so `expressionvariablesdevice:<device name>` is INFERRED, with `getByUID(0x...)` as the doc-verified rename-proof fallback. **Open questions:**

- subsystem:<ClassName> resolution: the LiveUpdate doc only shows subsystem:MonitoringManager and subsystem:RenderStreamSystem. D3NetManagerSystem and SessionSystem are Subsystem subclasses in the pyi (10341, 43090) but whether the lookup key is the class name for every subsystem must be tested live. If it fails, fall back to using the globals (d3NetManager / state) inside the property path with any working object, or discover the D3NetManager uid via fo-35 and use getByUID().
- Global names in the LiveUpdate eval namespace: the doc says 'all Designer types are available (via from d3 import *)'. d3.pyi has no __all__ and declares module-level d3NetManager, state, paths, resourceManager (lines 40-49), and the Python reference index lists them under 'Global Variables', so a plain import * should expose them - but the LiveUpdate context may be narrower than the /python/execute context. One NameError test settles it.
- What 'localMachine' means for a Companion connection to a non-Director: the LiveUpdate doc says subscribe messages are 'sent to the Director', and the Working-with-Sessions guide says to target the Director's hostname. If Companion points at an Actor/Understudy it is unknown whether expressions evaluate on that machine (localMachine = that Actor) or are forwarded. Recommend the module config note: connect to the Director; use d3NetManager.director/actors/understudies for the rest.
- Machine.role enum: no Options docstring on role (d3.pyi:24123); mapping Solo=0, DedicatedDirector=1, NonDedicatedDirector=2, Actor=3, Understudy=4, MobileEditor=5, UnknownRole=6 is inferred from Machine class constants (d3.pyi:23771-23887). Verify with a live read on a Director and an Actor.

- Machine.runningAs: assumed to be the failed Actor an Understudy is impersonating (mirrors REST health 'runningAsMachine'); confirm, and check what it returns when not taken over (self? null resource?).
- Discrepancy: D3Net guide writes d3net.directorMode = True and d3net.understudy = True, but the r34.0 pyi and the D3NetManager reference page mark directorMode/understudy read-only (no setter). Treated as read-only.
- Is there a Designer-expression prefix for the D3NetManager resource itself? D3NetManager.__username__ = 'd3net' (d3.pyi:10173) and Resource paths are 'objects/[class]/[name].apx', so something like d3net:<name> may resolve - no doc shows it and the resource name is unknown; do not ship without a test.
- Failover COMMANDS are not reachable through LiveUpdate set: D3State.cmdMachineFailed(hostname)/cmdMachineRestored(hostname) (d3.pyi:10749/10752) are methods, and a propertyPath calling them would execute on every evaluation - a hazard, never put them in a subscription. ### Dimension report: Designer expression (object path) syntax and Python 2.7 caveats

Target: Designer r34.0.3 / d3.pyi `__version__ = 'r34.0.256372'` (d3.pyi:22). All quotes below are verbatim from a page fetched in this task or from the local stub.

#### (a) Grammar of a resource reference

##### `type:name` form
- help.disguise.one accessing-resources: "The simplest and most readable method for building a reference to a known Resource in the system is to use the type:name syntax to refer to a Resource." and "to reference a Projector, the expression projector:"projector 1" is used to refer to the Projector itself. To reference a video clip which originates from a file in a subfolder, videoclip:"sample/george.jpg" can be used."
  https://help.disguise.one/designer/configuration/expressions/accessing-resources.html
- developer.disguise.one guides/expressions: "By Name: Use the type:name syntax. For example, projector:"projector 1" refers to a projector named "projector 1". If the name contains spaces or special characters, it's best to enclose it in quotes. If not, you can replace spaces and special characters with an underscore (_), like projector:projector_1."
  https://developer.disguise.one/python-api/guides/expressions

##### Names with spaces / special characters
- Quoted form is the current recommendation (above). Sanitised form: "In older versions of Designer, the quoted name syntax is not available. It is instead possible to reference names using a "sanitised" identifier. The name of "projector 1" referenced in the expression above would be sanitised to projector_1. Names in expressions are unable to contain spaces, dashes and other characters, which are valid for names in Designer. Any character which is not a letter in the alphabet, a number or an underscore must be replaced by an underscore (_). In older versions, this is not available for / characters." (accessing-resources)
- Layer-expressions page: "Names can only contain the characters a-z A-Z 0-9 _." and "This can cause conflicts when two Resources share the same name after normalisation" https://help.disguise.one/designer/configuration/expressions/layer-expressions
- The sanitised name is not the user-visible name: "projector:projector_1.description - this produces a text result which contains the real name of the Resource (without the _ character decoration.) i.e. "projector 1"." (accessing-resources)
- LiveUpdate doc uses both styles in the same document: `track:track_1`, `screen2:screen_1` and `Machine:\"<machine name>\"` (liveupdate.txt, raw HTML confirmed `Machine:` capital M and `track:` lowercase).

Recommendation for presets: use the quoted form for anything typed by an operator (`track:"Track 1"`), since Companion variables can contain spaces; document the underscore fallback.

##### Type prefix = lowercase Python class name (not `__username__`)
- LiveUpdate doc uses `screen2:screen_1` while d3.pyi:41825-41832 shows `class Screen2(Display)` with `__username__ = 'Surface'`. So the prefix is the internal class name, not the UI name.
- Resources guide (paths use the same rule): "The type in the path is always the internal type (i.e. never __username__) and always lowercase. A safe method to get the type part of a path for a known object is to use the type() function - type(my_obj).__name__.lower()." and Resource.path docstring d3.pyi:40513-40516: "Paths to internal resources are generally of the form `objects/[class]/[name].apx`, e.g. `objects/camera/cam1.apx`." https://developer.disguise.one/python-api/guides/resources
- Documented prefix examples: `projector:`, `videoclip:`, `transportmanager:default` (accessing-resources); `ledscreen:screen`, `camera:cam_1` (https://help.disguise.one/designer/configuration/expressions/examples/camera-angle-example); `track:`, `screen2:`, `Machine:` (LiveUpdate).
- Layers are the exception: they are referenced through `module:<layername>` — "module:NameOfModule.brightness*0.5 ... You cannot have any spaces in the layer name" (https://help.disguise.one/designer/configuration/expressions/linking-layers), `module:video.frameNumberDisplay` (layer-expressions), `module:this.brightness` (variables page). Caveat for LiveUpdate: "layer references are only valid for the period of time that the layer is active on the timeline" (layer-expressions). - Identifiers/fields/functions are case-sensitive: "Expressions are case-sensitive, so a variables or functions called hello are distinct from another called HELLO" (https://help.disguise.one/designer/configuration/expressions/expressions-overview); "Expressions are no longer case-insensitive - variables, fields and functions are looked up in a case-sensitive manner" (r27.10 note, https://help.disguise.one/designer/configuration/expressions/backward-compatibility).
- Case of the type prefix itself is NOT documented. The LiveUpdate doc's `Machine:` vs `track:` suggests the prefix is case-insensitive, but no source states it. Use lowercase (matches every help-site example and the path rule "always lowercase"). Open question.

##### `subsystem:`, `domain:`, `getByUID(...)`

Class name keeps its capitalisation there. d3.pyi:47736 `class Subsystem(_BlipValue)`, d3.pyi:27218 `class MonitoringManager(Subsystem)`, d3.pyi:40327 `class RenderStreamSystem(Subsystem)`.
- `domain:<name without "Domain" suffix>`: LiveUpdate uses `domain:MappedMedia` while the class is d3.pyi:24793 `class MappedMediaDomain(Domain)`. d3.pyi:14635 `class Domain(_BlipValue)`; DomainManager has `getDomainByType(self, type: Type) -> Domain` (d3.pyi ~14650).

#### (d) Python 2.7 caveats for propertyPath
- Version: "Designer uses Python 2.7 for its embedded interpreter ... Use Python 2.7 syntax and standard library features; Be aware of differences from Python 3 (e.g., print is a statement, not a function); String handling, division behavior, and dictionary methods differ from Python 3" https://developer.disguise.one/python-api/environment ; "This needs to be valid Python 2.7 code" https://developer.disguise.one/python-api/execution-api ; LiveUpdate: "Property paths are evaluated as Python expressions in an eval context. The variable object is bound to the resolved subscription object, and all Designer types are available (via from d3 import *)".
- Doc inconsistency to flag: guides/expressions shows f-strings in its Python examples (`seq.setExpression(f"module:{emitter_layer.name}.brightness")`, "Using an f-string is a clean way to build the expression") which contradicts the 2.7 statement on three other pages. Do not rely on f-strings.
- Concrete rules for propertyPath:
  1. `eval` = single expression. No statements: no assignment, `print`, `import`, `for`/`if` blocks, `def`, `lambda` bodies with statements. `:=` does not exist in 2.7.
  2. No f-strings (SyntaxError in 2.7). Use `"%s" % x` or `"{}".format(x)` (`.format` shown on the environment page).
  3. `/` on two ints floors in 2.7. Use `float(a)/b` or `1.0*a/b` for rates/percentages.
  4. Conditional expression `a if cond else b` (2.5+) is the None-guard for the property part, e.g. `object.timecode.statusString if object.timecode else ""`.
  5. List/dict/set comprehensions and generator expressions are all valid in 2.7 (dict comprehensions are used in the LiveUpdate doc). `next(...)`, `sorted`, `min`, `max`, `len`, `range`, `getattr(obj, "name", default)`, `hasattr` (useful-strings uses hasattr) all exist.
  6. `object` shadows the Python builtin `object` inside the eval namespace; do not use `isinstance(x, object)`.
  7. `sys` and `threading` are removed (environment page). `math` is not imported by `from d3 import *`; availability inside the LiveUpdate eval namespace is unverified.
  8. Unicode: 2.7 has separate `str`/`unicode`; string values serialise fine to JSON; string comparisons with literals work. Avoid non-ASCII literals in the path.
  9. Long ints and `0x...` literals are fine (UIDs).
  10. Values produced by comprehensions/method calls are read-only for `set` ("will return all video layers on the named track, but will not allow the client to change any of those layers" - LiveUpdate). Only direct attribute chains ending in a settable property/field (`.v`, `.offset`, `.brightness`) accept `set`.

### Blocking questions before Phase 1

1. Type-prefix casing and quoting for object paths: docs show transportManager:default (plugin guide, HELP.md), transportmanager:default (help accessing-resources), Machine:"<name>" (LiveUpdate doc), lowercase-only 'always lowercase' paths (resources guide) and class-cased useful-strings paths; and(x,y)/or(x,y) are functions not infix operators. The catalog cannot fix a canonical spelling without one live test per casing on r34.0.3.
2. Does subsystem:<ClassName> resolve for every Subsystem subclass (D3NetManagerSystem, SessionSystem, GuiSystem) or only for the two documented ones (MonitoringManager, RenderStreamSystem)? This gates all director-relative failover presets (fo-21..fo-35), tr-48 and every 'local machine' readout.
3. Are module globals (d3NetManager, state, paths) and bare type names (ReleaseVersion, ExpressionVariable.FloatType, MetricGraphCategories) available inside a LiveUpdate property path? The doc says 'all Designer types are available (via from d3 import *)' - types, not globals. Gates fo-17, fo-22, fo-38..fo-43, mon-categories.
4. Expression-variable path: does 'expressionvariablesdevice:<name>' resolve, and does a LiveUpdate set through object.container.variables[<i>].defaultFloat write the live value? Until answered the whole Expression Variables category has zero shippable presets; getByUID read is the only doc-verified fallback.
5. Monitor-name list: only fps, GPUProfiler, CPU, GPUMemory, ProcessMemory (guide) and Machine, Disk (Grafana) are evidenced; Output Latency, Frame Latency, PCI/CPU IO, Timer and the RenderStream graphs have no known findLocalMonitor name. Needs the discovery expression [m.name for m in object.localMonitors().all()] run live, plus [s.name for s in object.graphDescriptor(False).dataSeries] per monitor to confirm series titles, plus a unit check for CPU 'Total' (ms vs percent).
6. Transport reachability details: tRender vs tCurrent (which one the timeline readout follows), PlayMode.__str__() literal strings, JSON shape of object.player.playMode, whether a LiveUpdate set on object.brightness/volume/engaged (and TrackPlayer.mode) behaves like a TransportCommand, and how to express a boolean 'TC locked' (no pyi member matches REST receivingTimecode).
7. Set semantics beyond the single documented example: scalar sub-field sets (object.offset.x - advertised in HELP.md but undocumented), set through list subscripts/comprehensions, set on a live Module field vs keyframe, set on locked resources, and whether a set on a Subsystem-rooted (non-Resource) path such as MonitoringManager.searchString is accepted.
8. Track/layer stub-vs-doc conflicts requiring a live test before any layer preset ships: getLeafLayers() with no argument on a Track, nKeys vs nKeys(), layer-by-name via track:<t>.findLayerByName("..") in the object path, and track:"Track 1" quoting. HELP.md's 'track:track_1 / object.enabled' Boolean example must be re-checked: d3.pyi 47975-50140 shows no 'enabled' on SuperTrack/Track, only enableRender(onOff).
9. RenderStream workload discovery: the workload ID (int, decimal or hex?) is only obtainable via REST or the widget's Copy UID, which the module cannot call; and enum meanings for WorkloadInstance.status / WorkloadHealth.status / priority are undocumented, so button colours cannot be mapped without a live capture.
10. Error/throttle behaviour that shapes preset defaults: what the {error} reply looks like for an unknown monitor/name/index (the module auto-unsubscribes after 3 consecutive path errors per HELP.md, so a preset with a placeholder name will self-disable), whether computed expressions (method calls, comprehensions) are re-evaluated per updateFrequency cycle rather than change-driven, and confirmation that updateFrequency 0 must be banned for monitors and transport playhead (the shipped presets.ts uses 0).
11. Which machine evaluates expressions when the Companion connection targets a non-Director, and whether remote monitors require MonitoringManager.useMonitorByName(nodeName, monitorName, True) on the Director before data flows.
12. Module-level Templates question: which option fields in src/feedbacks.ts / src/actions.ts declare useVariables (Companion only rewrites $(liveupdate:...) inside useVariables textinput or expression fields on connection rename), and whether textExpression styles are acceptable given the module-base 1.13.2 -> Companion >= 4.1 floor.
